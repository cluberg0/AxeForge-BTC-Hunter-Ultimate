# Аудит API, OTA и сохранения настроек

Проверен оригинальный AxeForge v1.4.10, commit `e84c651c36a4b5f91c537577704245ded032592d`, и интеграция RU-FIX10. Это аудит исходного кода и испытания на хосте. Физическая OTA-установка, работа датчиков и аварийных отключений на Gamma 601 не выполнялись.

## Исправления

1. В `ota_post` потерявшийся клиент мог бесконечно удерживать единственную задачу HTTP: `HTTPD_SOCK_ERR_TIMEOUT` всегда приводил к повтору. Теперь три последовательных тайм-аута приёма (настройка сервера — 15 с) прекращают загрузку и освобождают OTA handle. Полученные данные обнуляют счётчик, поэтому временные задержки Wi-Fi допускаются. При отказе новый boot partition не выбирается и перезапуск не планируется.
2. `settings::load` разыменовывал невыделенный буфер при нехватке памяти для JSON пулов, а также разбирал буфер при ошибке чтения NVS. Теперь оба отказа журналируются, некорректные данные не разбираются, NVS не стирается. В памяти остаются значения по умолчанию, ранее сохранённый NVS остаётся доступным после успешного перезапуска.
3. Добавлена полная отдельная OpenAPI 3.0.3 спецификация нативных дополнений `overlay/docs/native-api.json`; пути добавляются в штатный `docs/openapi.yaml` при подготовке исходников. Описаны единицы, позиции 20 полей архива, пустые значения, состояния кандидата, неопределённость timing trial и различие pool ACK/Bitcoin confirmation. Контроль сверяет ключи реального кода, спецификации и JSON, полученный из исполняемых host-тестов.

Все изменения воспроизводит `patch_api_safety.py`; повторное применение отвергается, чтобы не наслаивать патчи.

## Проверенные инварианты исходного кода

- `boards/gamma.toml`: `id=gamma`, `chip=bm1370`, `count=1`, штатный режим 525 MHz / 1150 mV. Пределы Kconfig 800 MHz / 1300 mV не изменены. Сами `board_bitaxe.cpp`, `gates.cpp`, `tps546.cpp`, аппаратные пределы Kconfig и `ota_guard.cpp` остаются без diff относительно upstream.
- `partitions.csv` не изменён. SHA-256 исходного и итогового файла: `9cd1bfe99b6ecc76648063541f4e78dc42d9693ad95e2b65500f26d3ded74e57`. NVS `0x9000 + 0x6000`; OTA app-разделы по 4 MiB. Передаётся только app image, никакой factory image или таблицы разделов.
- Для семейства Bitaxe начальная ошибка NVS не ведёт к `nvs_flash_erase`; используется штатная попытка возврата к stock firmware. Импорт `main` namespace AxeOS открывает его только `NVS_READONLY`. Оригинальные настройки AxeForge остаются в `axeforge`, модули используют `af_intel`/`af_hunter`.
- Новые маршруты зарегистрированы в том же массиве, что штатные. Каждый `/api/` оборачивается `api_guard`: локальный Host, ограничения setup AP, X-AxeForge и same-origin для изменений, сессия OTP при включённой 2FA. GET не требует сессии по штатной модели AxeForge.
- `fwupdate::Writer`: запись в следующий app-раздел, последовательное стирание секторов, проверка `0xE9`, поиск тега `AXEFORGE-BOARD:gamma;` с учётом границ фрагментов, `esp_ota_end` перед выбором boot partition. Деструктор прекращает незавершённую запись.
- OTA Guard включён по умолчанию, автоматическое внешнее обновление выключено. Сохранённые пользовательские значения этих параметров не переписываются модификацией.
- Штатный Guard выбирает предыдущий раздел после двух crash-restart новой версии или после десяти минут онлайн без нормального майнинга; две минуты нормального майнинга завершают probation. Пауза, перегрев или отсутствие сети не являются автоматическим доказательством плохой прошивки. Защита зависит от доступности NVS и сохранённого предыдущего образа; это не гарантия восстановления после любого отключения питания.
- Новые GET не раскрывают Wi-Fi, pool password, wallet или токен уведомлений. Кандидат содержит только hash, индекс исходного пула и состояние; pool acceptance явно не назван подтверждением Bitcoin.

## Выполненные проверки

- `python3 upstream/scripts/api_contract.py` — exit 0, все семь штатных source-контрактов API.
- Оба C++ host-теста нативных модулей с `-Wall -Wextra -Werror -fsanitize=address,undefined` — exit 0; `AXEFORGE_API_JSON=1` выводит реальный ответ обработчика, в том числе архивную строку из 20 полей.
- `python3 scripts/check_native_api.py upstream --json-dir reports/api-json` — exit 0, ключи GET/POST и штатная обёртка защиты совпадают, оба реальных JSON проходят схему.
- `python3 tests/api_safety.py upstream` — exit 0. Из итогового исходника извлекается и исполняется настоящий OTA-обработчик с подменой socket/flash API: три тайм-аута, временные задержки с восстановлением, обрыв, отказ malloc, отсутствующий раздел, малый/слишком большой файл. Отдельно исполняется настоящая ветка чтения сохранённых пулов с отказами malloc, запроса размера и чтения NVS. Все варианты под ASan/UBSan.

Проверки подтвердили поведение программы в моделируемых отказах. Они не моделируют задержки реальной flash, аппаратную гонку питания, EEPROM/NVS на конкретной плате или аппаратное восстановление.

## Ограничения, требующие честного описания выпуска

- Bitcoin mainnet подтверждается консенсусом и цепочкой заголовков. Даже exact target/pow-limit и pool ACK дают локального кандидата и ответ пула; прошивка не является полным Bitcoin-узлом.
- Имя известного BTC-пула — ограничение области расчёта, а не криптографическое подтверждение сети. Невозможно удостоверить добросовестность удалённого пула одним hostname.
- BCH/DGB/SPACE/FB/XEC — отдельные пользовательские шаблоны. Проверка SHA-256d, адресов конкретной сети, Stratum и выплат должна быть явной; работа любого неподтверждённого пула не доказана. Штатный валидатор BTC payout нельзя автоматически выключать ради альтернативного профиля.
- Сравнение задержки по наблюдаемым новым блокам и времени передачи драйверу не доказывает начало хеширования ASIC. Рекомендация не переключает пул автоматически, небольшая выборка не доказывает преимущество.
- Нельзя утверждать тестирование Safari iOS, физического BM1370, power loss/NVS recovery или работу 30 W без аппаратного испытания. Результаты Chromium/WebKit указываются отдельно в общем отчёте.
